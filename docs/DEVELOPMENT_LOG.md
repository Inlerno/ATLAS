Занятость имитировалась блокировкой байта RESERVED файла `data\atlas.db` (`0x40000001`, как у процесса с транзакцией записи; файл не пишется). Для обычных запусков сценарий сообщил, что SHA-256 базы не изменился; для запусков с занятой базой эта строка вывода владельцем не передана.

**Почему при занятой базе проба не ждала.** Проба записи открывает транзакцию `BEGIN` в режиме `DEFERRED` (`sqlx-core 0.8.6`), проверяет режим журнала, читает `PRAGMA user_version` — после этого транзакция уже читает — и только затем пишет. Запись требует повысить транзакцию чтения до транзакции записи, а другое соединение уже держит блокировку записи. В этом случае SQLite не вызывает обработчик занятости и сразу возвращает `SQLITE_BUSY`, потому что ожидание могло бы закончиться взаимной блокировкой:
- документация [busy_handler](https://www.sqlite.org/c3ref/busy_handler.html): если вызов обработчика может привести к взаимной блокировке, SQLite возвращает `SQLITE_BUSY`, не вызывая его; её пример — один процесс повышает блокировку чтения до RESERVED, а другой держит RESERVED и ждёт EXCLUSIVE. Замер имитировал второго только удержанием RESERVED, но правило в исходнике безусловное (следующий пункт);
- документация [lang_transaction](https://www.sqlite.org/lang_transaction.html), раздел 2.1: если другое соединение уже меняет базу, повысить транзакцию чтения до записи нельзя, и оператор записи завершается `SQLITE_BUSY`;
- исходник `sqlite3.c` 3.54.1: `sqlite3PagerSetBusyHandler` — переход SHARED → RESERVED обработчик не вызывает; `sqlite3BtreeBeginTrans` повторяет попытку с обработчиком только при `pBt->inTransaction==TRANS_NONE`.

Хранилище при этом — `Unavailable`, как записано в ADR-016; результат замера: `SQLITE_BUSY`, 2–3 мс.

**Это не значит, что `busy_timeout` никогда не даёт ожидания.** По исходнику (`sqlite3PagerSetBusyHandler`, `sqlite3BtreeBeginTrans`) SQLite вызывает обработчик, когда транзакция без блокировок получает блокировку чтения (другой процесс в это время фиксирует запись), когда запись начинается без предварительного чтения (в том числе `BEGIN IMMEDIATE`), и при `COMMIT`, пока у других соединений открыто чтение. Ни один из этих случаев на ATLAS не измерялся.

**`BEGIN IMMEDIATE`** берёт блокировку записи сразу, до любого чтения ([lang_transaction](https://www.sqlite.org/lang_transaction.html), раздел 2.2), поэтому при занятой базе ведёт себя иначе: по исходнику он ждёт до `busy_timeout` и только затем возвращает `SQLITE_BUSY`. Хранилище его не использует. Ожидание через `BEGIN IMMEDIATE` на ATLAS **не проверялось**, и не доказано, что такая транзакция не меняет файлы WAL до проверки режима журнала (мера 4 ADR-016). Это открытый вопрос для MM-5B.

Миграций пока нет (`MIGRATIONS = &[]`), запуск с миграцией не измерялся.

**Вручную по-прежнему не проверялись**: списки доступа (ACL), антивирус и индексатор, завершение сеанса Windows, `-SelfTest` в PowerShell 7 на ПК владельца.

## 2026-11-15 — Issue #26: гонка WAL при открытии хранилища (TOCTOU)

> Дополнение 2026-11-17: PR #27 слит в `main` 2026-11-15 (`5d6ede8`). Утверждения ниже о том, что исправление «в `main` пока не слито» и что ручной проверки не было, верны на дату записи; актуальное состояние — запись от 2026-11-17.

Отдельная работа: [Issue #26](https://github.com/Inlerno/ATLAS/issues/26). PR #25 добавил первоначальную SQLite Foundation и слит в `main` 2026-11-15 (`0580304`) **без** этого исправления: гонка обнаружена после его слияния. Исправление опубликовано отдельным [PR #27](https://github.com/Inlerno/ATLAS/pull/27) из той же ветки `feature/sqlite-foundation` (новая ветка не создавалась — решение пользователя) и в `main` пока не слито. Независимое ревью нашло окно между проверкой режима журнала и записью: файл `atlas.db-wal`, появившийся после проверки, подхватывался следующим оператором, и проба записи или миграции писали в чужой WAL (воспроизведено: WAL 12 392 → 32 992 байта, файл базы без изменений). Решения утверждены пользователем; запись — ADR-016.

### Что сделано
- **Проверка режима внутри транзакции.** Проба записи и миграции: `BEGIN` → чтение файла → `PRAGMA journal_mode` → работа только при `delete`, иначе `ROLLBACK` и `Unavailable` (`step=probe-journal-mode`, `step=migrations-journal-mode`). Так же — читающая проверка миграций ветки `ReadOnly`. Прежние проверки (после первого чтения и итоговая) сохранены.
- **Миграции одного запуска атомарны.** Одна внешняя транзакция: проверка режима → `Migrator::run_direct` без изменений → `COMMIT` после успеха всего набора; ошибка миграции — `ROLLBACK` набора; ошибка `COMMIT` — `Unavailable` (`step=migrations-commit`). **Изменение поведения:** раньше при ошибке второй миграции первая оставалась применённой; теперь не остаётся ничего. Тест `failed_migration_leaves_no_trace` заменён на `failed_migration_rolls_back_the_whole_run` — ожидание изменено по утверждённому решению, а не ослаблено.
- **Совместимость `run_direct` с внешней транзакцией** — по исходному коду `sqlx 0.8.6`: `Migrate::apply` (`vendor/sqlx-sqlite/src/migrate.rs`) вызывает `self.begin()` и `tx.commit()`; поток соединения (`src/connection/worker.rs`) по счётчику глубины выполняет на глубине 0 `BEGIN`, глубже — `SAVEPOINT _sqlx_savepoint_N`, а при фиксации — `COMMIT` только на глубине 1, иначе `RELEASE SAVEPOINT` (`sqlx-core/src/transaction.rs`: `begin_ansi_transaction_sql`, `commit_ansi_transaction_sql`, `rollback_ansi_transaction_sql`). Внутри внешней транзакции мигратор внешний `COMMIT` не выполняет; при ошибке миграции её транзакция уничтожается (откат к точке сохранения), ошибка возвращается вызывающему. Блокировки мигратора для SQLite — пустые операции.

## 2026-11-10 — Issue #9 (PR #20): исправления D1, D2, L1 до слияния

Исправления обязательны до слияния PR #20 (решение пользователя 2026-11-10). Технический план согласован пользователем: `claude/PR20_FIX_PLAN.md`, редакция 3 (документ проекта Claude, не репозитория). Архитектурные контракты, публичный API, статусы, тексты, таблица сроков ADR-014 и семантика прерывания `initialize` / `start` не менялись. Новых зависимостей и features нет.

### Что исправлено
- **D1 — паника или зависание `Drop` в задаче менеджера** (`manager.rs`). Раньше экземпляр удалялся в задаче менеджера в четырёх местах: после `stop`, после ошибки вызова, при принудительном завершении и в конце цикла. Паника `Drop` раскручивала менеджер, зависание останавливало его. Теперь:
  - экземпляр удаляется на пуле блокирующих потоков (`spawn_blocking`); ожидание — остаток того же `STOP_TIMEOUT`, что и у `stop` (после ошибки `initialize` / `start` — `STOP_TIMEOUT`), не позже общего срока выхода;
  - паника или срок удаления после успешного `stop` → `Failed { Stop }` с прежними текстами; причину различает журнал (`call = "drop"`); в статусе остаётся первая ошибка: `stop`, удаление, прерванные задачи;
  - при ошибке `initialize` / `start` — порядок решения 7: `Failed { phase }` → отмена токена → удаление → ожидание задач; зависший `Drop` не задерживает `Failed`. В первой версии PR #20 экземпляр на этом пути удалялся раньше `Failed` (уточнение к решению 7 записи #9 ниже);
  - удаления, которые менеджер не дождался, не прерываются (это невозможно), их результат не читается; ещё не завершившиеся к концу `shutdown_all` перечисляются в журнале (`warn`) до ответа на выход.
- **D2 — сбои фоновых задач после запроса выхода** (`manager.rs`, `context.rs`). Раньше отчёт, прочитанный после запроса выхода, запускал `Failed { Run }`, остановку и каскад, а отчёты, пришедшие во время остановки модулей, удалялись вместе с очередью. Теперь:
  - после запроса выхода отчёт только пишется в журнал: `warn` — экземпляр работал на момент выхода, `debug` — уже остановлен; текст ошибки сохраняется; статус не меняется, итог даёт остановка в `shutdown_all`;
  - после остановки модулей менеджер разбирает очередь (порядок — L1 ниже): отчёты — в журнал, команды — `ShutDown`, `HealthCheckEnded` — без действий и без записи, повторный запрос выхода — `ShutDown` после строки о завершении, до ответа;
  - отчёт, который уже нельзя отправить менеджеру, супервизор пишет в журнал сам (`warn`).
- **L1 — `module manager stopped` после ответа** (`manager.rs`). Строка пишется до ответа на `Shutdown`; после ответа менеджер ничего не пишет, не публикует и не выполняет. Для теста — точка перехвата `#[cfg(test)]` сразу после ответа (как в `events::bus`).
- **Порядок завершения менеджера — вариант B** (ревью реализации, решение пользователя 2026-11-10): разбор очереди без закрытия (`try_recv`) → `module manager stopped` → `close()` и разбор остатка (`recv` до `None`) → освобождение повторных запросов выхода → ответ. Причина: запрос, нашедший очередь закрытой, сразу получает `ShutDown`. В первом варианте исправления очередь закрывалась до строки о завершении, и запасной путь `RunEvent::Exit` (`restart` из другого потока или завершение сеанса Windows во время начатой остановки) мог получить `ShutDown`, вызвать `flush_logs()` и потерять строку. Теперь закрытие идёт после строки.
- **Тестовая заглушка** (`testing.rs`): поведение `Drop` (обычное, паника, блокировка до сигнала теста, не дольше 30 с), счётчик завершённых удалений, число живых фоновых задач в момент удаления.
- **Документация:** ADR-014 (изоляция удаления, примечание к таблице сроков, порядок остановки и ошибок запуска, исключение для режима выхода, разбор очереди, пределы удаления; расхождения Н2–Н5 устранены), `ARCHITECTURE.md`, doc-комментарии `Module`, `ModuleContext::spawn`, менеджера. ### Ограничения
- Зависший `Drop` срок не прерывает: поток пула занят до конца `Drop` или до выхода процесса; освобождение ресурсов к ответу на выход не гарантируется.
- Если `stop` израсходовал почти весь срок, даже быстрый `Drop` получит `TIMED_OUT`; после общего срока выхода удаление не ждётся (`SHUTDOWN_DEADLINE`).
- Вариант B: отчёт о сбое, пришедший около момента закрытия очереди (между разбором без закрытия и `close()`), пишется после `module manager stopped`, но до ответа. Если запасной путь `RunEvent::Exit` в этот момент уже получил `ShutDown` на запрос, отправленный после закрытия, и сбрасывает журнал, эта строка может потеряться. Строка о завершении и всё, что пришло до неё, не теряются.
- `restart` из главного потока (Tauri `process::restart`) не даёт `RunEvent` и обходит остановку модулей — существующий пробел MM-4, вне D1–L1; в коде приложения `restart` не вызывается.
- Строки супервизора и panic hook после `flush_logs()` теряются (ограничение журнала MM-1).

### Решения, которых нет в тексте #9 (приняты пользователем 2026-11-09 по ревью PR #20)
Записаны в ADR-014 («Принятые решения») и как решение 29 в #13. Нумерация совпадает с описанием PR.
1. **`async-trait` не добавлен**: используются ручные `Pin<Box<dyn Future + Send>>` — вариант, предусмотренный #9.
2. **`macros` не подключён** (решение 27): вместо `select!` используется `CancellationToken::run_until_cancelled`.
3. **`Module: Send + Sync`**: future от `health_check(&self)` должен быть `Send`.
4. **Проверка health без ответа держит экземпляр.** Экземпляр остаётся у проверки и не теряется, состояние не меняется. Новая проверка не запускается. Поздний ответ возвращает экземпляр, поздняя паника → `Failed { HealthCheck }` с каскадом. При остановке менеджер ждёт проверку в пределах таймаута `stop`; если ответа нет — модуль останавливается без вызова `stop` (`Failed { Stop }`).
5. **`HealthChanged`** публикуется только при изменении значения.
6. **`stop` не вызывается** после неудачных `initialize` / `start`: экземпляр не запускался. Его фоновые задачи отменяются и прерываются менеджером.
   - **Уточнение пользователя:** модуль сам освобождает частично выделенные ресурсы до возврата ошибки, а удаление экземпляра не должно оставлять ресурсов. Это записано в контракте `Module` (`contract.rs`) и в ADR-014.
7. **`Failed` выставляется сразу** при обнаружении сбоя, освобождение ресурсов идёт после. Для сбоев во время работы это порядок из #9; для остальных сбоев — тот же. *Уточнение 2026-11-10:* при ошибке `initialize` / `start` экземпляр в этой версии удалялся раньше `Failed`; исправлено в D1 (запись выше).
8. **Запрос выхода** прерывает идущие `initialize` / `start` / `health` сразу. Оставшиеся шаги плана пропускаются (`interrupted`). После запроса `apply` и `check_health` возвращают `ShutDown`.
9. **Двухфазный выход**: `ExitRequested` + `prevent_exit` + повторный `exit()`; запасной путь в `RunEvent::Exit`.
10. **Тексты для пользователя** написаны по-русски, как «проверка не ответила» в #9, и собраны в `manager::text`. Ошибка, которую вернул сам модуль, показывается как есть: контракт `ModuleFailure` требует, чтобы текст был безопасным для показа.
11. **Некорректный каталог**: приложение работает без модулей. Встроенный каталог проверяется тестом.
    - **Уточнение пользователя:** ошибка обязательно пишется в лог на уровне `error` вместе с причиной, молчаливого игнорирования нет. Это проверяет тест `an_invalid_catalog_is_logged_and_leaves_the_manager_without_modules`. Мутационная проверка: без записи в лог и с уровнем `warn` тест падает.
12. **Значения таймаутов** и их обоснование — в ADR-014.

Ограничение таймаутов записано явно — в контракте `Module`, в ADR-014 и в `ARCHITECTURE.md`. Асинхронный таймаут прерывает вызов только там, где тот уступает управление. Блокирующий нативный код так прервать нельзя, поэтому модуль выносит его в отдельный поток.

**Найдено при самопроверке и исправлено в коде.** При `restart` Tauri не позволяет отложить выход, и модули останавливает запасной путь в `RunEvent::Exit`. Фоновая остановка, закончив, запрашивала бы выход ещё раз. На уже завершающемся цикле событий Tauri обрабатывает такой запрос через `std::process::exit`, и процесс мог закончиться раньше сброса логов. **Найдено и исправлено в тестах.** Тест «детали паники — только в лог» иногда не видел записей лога при параллельном запуске. Причина — кеш интереса `tracing` к местам логирования. Он общий для процесса: пока зарегистрирован один подписчик, интерес нового места вычисляется по подписчику того потока, который первым до него дошёл. Параллельный тест без подписчика кешировал «не интересно», и подписчик теста, заданный для его потока (`set_default`), этих записей не получал. Теперь в бинаре unit-тестов один глобальный подписчик с буфером на поток.

**Стабильность** (облачный Linux): без сбоев прошли 100 прогонов тестов модулей, 50 прогонов всех unit-тестов, 30 — на одном ядре, 20 — в один поток.

## 2026-11-09 — Issue #8: MM-3 — центральная шина событий

Центральная типизированная шина уведомлений: `src-tauri/src/events/{mod,types,bus}.rs`. Решение — ADR-013 (включает решения 24 и 25 из #13); описание — раздел «Event Bus» в `ARCHITECTURE.md`.

### Что сделано
- `types.rs`: `EventEnvelope { seq, at_unix_ms, source, event }`, `EventSource::Core`, `AppEvent::Module(ModuleEvent::StatusChanged { id, previous, current })`.
- `bus.rs`:
  - `EventBus` — клонируемый handle: `new(capacity)`, `publish(event) -> Result<seq, BusClosed>`, `subscribe()`, `close()`;
  - `Subscriber::recv()` → `Received::Event` / `Lagged { missed }` / `Closed`.
- `AppState` хранит шину. На `RunEvent::Exit` шина закрывается (`close_events`), затем сбрасывается лог — строка `event bus closed` попадает в файл.

### Уточнения в рамках #8 (приняты пользователем 2026-11-09 по ревью PR #17)
Зафиксированы в ADR-013 и в решении 27 в #13.

- **`EventSource::Module(ModuleId)` не добавлен.** Его отправитель — публикация модулями, а она вне скоупа #8 (впервые в #12). Без отправителя вариант не создаётся нигде, и тестовая сборка не проходит `clippy -D warnings`. Обойти это можно только искусственным тестом или точечным `allow`. Поэтому вариант добавляется вместе с отправителем — по тому же правилу, что и варианты событий (решение 5 в #13). Поле `source` и правило «источник проставляет ядро» действуют уже сейчас.
- **Явное закрытие `close()`.** `App::run` завершает процесс через `std::process::exit`, поэтому handle шины в `AppState` никогда не удаляется. Без явного закрытия подписчики не получили бы `Closed`.
- **Ёмкость — только степень двойки до 4096.** `tokio` 1.54.1 округляет ёмкость вверх до степени двойки (так сказано в его документации). Поэтому другие значения отклоняются, а не округляются молча. Неверное значение — ошибка в коде и вызывает панику при создании. Для `DEFAULT_CAPACITY` корректность проверяется при компиляции, поэтому `setup` паниковать не может.
- **`macros` не подключён:** зависимости не добавляются только ради удобства тестов. Тесты запускают futures на `tokio::runtime::Builder::new_current_thread()` (feature `rt`), поэтому `tokio-macros` в `Cargo.lock` не появился.
- В однопоточных тестах сообщение уже должно ждать подписчика: тест опрашивает `recv` один раз и падает, а не зависает.

### Детерминированная проверка порядка (по ревью PR #17)
Первая версия проверяла одновременную публикацию только стресс-тестом и ловила нарушение порядка не в каждом запуске (27–29 из 30). По запросу пользователя добавлены тесты, которые воспроизводят нужное чередование потоков синхронизацией, а не ждут случайной гонки. Архитектура шины не менялась.
- **Точки перехвата** — модуль `test_hooks` в `bus.rs`, компилируется только в тестовой сборке (`#[cfg(test)]`); в приложении их нет. Хуки задаются для отдельного потока (`thread_local!`), поэтому параллельные тесты друг другу не мешают:
  - `BEFORE_SEND` — вызывается в `publish`, когда у события уже есть `seq`, но оно ещё не отправлено (блокировка шины удерживается). Тест останавливает в этой точке публикующий поток;
  - `BEFORE_WAIT` — вызывается, когда поток собирается ждать блокировку шины, занятую другим потоком. Так тест точно знает, что поток ждёт, и не угадывает это по времени.
- **Тесты:**
  - `overlapping_publications_are_delivered_in_seq_order` — A получил `seq` 1 и остановлен перед отправкой; B и C начинают публикацию и оба обязаны ждать; после продолжения A три подписчика получают события строго в порядке `seq`, и `seq` каждого события совпадает с числом, которое вернул его `publish`;
  - `close_waits_for_a_publication_in_progress` — `close` во время публикации ждёт её; событие доставляется до `Closed`;
  - `subscription_during_a_publication_starts_after_it` — `subscribe` во время публикации ждёт её; новый подписчик получает только следующие события.
- Стресс-тесты (8 потоков × 400 событий; закрытие при гонке) сохранены как дополнительная проверка случайных чередований.
- В документацию API (`bus.rs`, ADR-013, `ARCHITECTURE.md`) добавлено **требование к использованию**: waker задачи, ожидающей `recv`, не должен синхронно вызывать шину — подписчики пробуждаются под блокировкой шины.

## 2026-11-09 — Issue #6: ядро — модель ошибок, логирование, состояние приложения

### Решения (согласованы пользователем)
- **Fallback логирования.** Если файловый лог недоступен, приложение пишет только в stdout с предупреждением и продолжает работать. Сбой файлового логирования не останавливает приложение; `setup` никогда не возвращает ошибку (иначе Tauri паникует).
- **Ротация.** Новый файл раз в сутки, хранятся последние **7** файлов (`MAX_LOG_FILES`, включая текущий); старые удаляются автоматически.
  - Удаление выполняет `tracing-appender` 0.2.5: при создании appender'а (старт приложения) и при каждой смене дня. Удаляются только обычные файлы с префиксом `atlas` и суффиксом `log`, самые старые по времени создания.
  - Это не только заявлено: тест `rolling_appender_keeps_at_most_max_log_files` (10 старых файлов → ровно 7, посторонние файлы не тронуты) **падает**, если убрать `.max_log_files(...)` (проверено мутацией: `left: 11, right: 7`).
- **Путь к логам на Windows:** `%LOCALAPPDATA%\com.inlerno.atlas\logs\atlas.YYYY-MM-DD.log`. Дата в имени и момент ротации — по **UTC** (`tracing-appender`), для Калининграда это 02:00.
- **Сброс буфера при выходе.** `tauri::App::run` завершает процесс через `std::process::exit`, деструкторы управляемого состояния не вызываются. Поэтому guard логов хранится в `AppState` и явно сбрасывается в `flush_logs()` на `RunEvent::Exit`. `flush_logs()` идемпотентен, переживает отравленный мьютекс и одновременные вызовы.
- **Фильтр уровня:** `RUST_LOG`, иначе `info`. Значение передаётся в чистую функцию; тесты не меняют окружение процесса (`std::env::set_var` — `unsafe` в Rust 2024).
- Сообщения крейта `log` (в том числе от Tauri) перенаправляются в `tracing` (feature `tracing-log`).
- Panic hook пишет панику в лог (`target: panic`) и вызывает предыдущий hook — стандартное поведение сохраняется.

### Зависимости
Прямые (features объявлены явно):

| Крейт | Версия | Лицензия |
|---|---|---|
| `thiserror` (`std`) | 2.0.21 | MIT OR Apache-2.0 |
| `tracing` (`std`, `default-features = false`) | 0.1.44 | MIT |
| `tracing-subscriber` (`std`, `registry`, `fmt`, `ansi`, `env-filter`, `tracing-log`) | 0.3.23 | MIT |
| `tracing-appender` | 0.2.5 | MIT |

Новые транзитивные пакеты в `Cargo.lock` (только добавления, версии существующих не менялись): `lazy_static` 1.5.1, `matchers` 0.2.0, `nu-ansi-term` 0.50.3, `sharded-slab` 0.1.7, `symlink` 0.1.0, `thread_local` 1.1.10, `tracing-log` 0.2.0, `valuable` 0.1.1 — все MIT или MIT/Apache-2.0.

- `tracing` объявлен с `default-features = false`: feature `attributes` (`#[instrument]`) в коде не используется. Поэтому proc-macro `tracing-attributes` 0.1.31 больше не входит в `Cargo.lock`. Других потребителей у него нет: `softbuffer` (Windows) подключает `tracing` с `default-features = false`.
- `valuable` 0.1.1 есть в `Cargo.lock`, но **не компилируется** ни для одной целевой платформы. Это опциональная зависимость `tracing-core`, которая включается только флагом `--cfg tracing_unstable`, а lockfile перечисляет все такие варианты. Лицензия MIT указана в метаданных; файла лицензии в опубликованном пакете нет.

### Ограничения
- При принудительном завершении процесса (`taskkill /F`, сбой нативного кода) последние буферизованные записи могут потеряться — `RunEvent::Exit` не наступает. Окно потерь мало: рабочий поток пишет непрерывно (эксперимент: очередь в 50 000 строк сброшена за 7,6 мс).
- Сообщения, появившиеся до `setup`, в файл не попадают.
- **Fallback не виден в Windows Release.** Release-сборка использует `windows_subsystem = "windows"`, консоли нет. Поэтому в режиме fallback (только stdout) предупреждение и сами логи пользователю не видны. Показ состояния логирования в UI — задача будущей диагностики.
- **Новый файл не удалось создать после смены дня.** `tracing-appender` пишет `Couldn't create writer for logs` в stderr и продолжает писать в прежний файл; приложение не падает. Если папку логов удалили во время работы, она создаётся заново при следующем открытии файла. Старые файлы удаляются до создания нового, поэтому лимит 7 сохраняется.
- **Паника внутри форматирования лог-сообщения.** Например, паника в `Debug`-реализации значения, переданного в событие. Взаимоблокировки нет: `tracing-core` при повторном входе направляет вложенное событие в пустой диспетчер. Но наш panic hook такую панику в лог **не** записывает — её выводит в stderr предыдущий (стандартный) hook. Проверено экспериментом.
- **Сбой моста `log` → `tracing`.** `try_init()` сначала ставит глобальный подписчик, затем `LogTracer`. Если до `setup` уже установлен другой `log`-логгер, `init` вернёт ошибку уже после установки подписчика: guard файлового лога удалится, и запись в файл молча прекратится (stdout продолжит работать). В ATLAS такого логгера нет (`tauri-plugin-log` не используется), поэтому случай сейчас недостижим. Решение пользователя: в коде не исправлять, только задокументировать.
- Записи после `flush_logs()` и сверх буфера в 128 000 строк отбрасываются без паники (режим `lossy` неблокирующего writer'а). Сброс при выходе ограничен ≈1,1 с (таймауты `WorkerGuard::drop`), поэтому выход не зависает.
