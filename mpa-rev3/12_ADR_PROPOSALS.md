## ADR-017. Мультиплатформенная архитектура, режимы работы и владение данными

- **Контекст.** Направление владельца: Android и iOS; мобильное приложение — и пульт Desktop, и самостоятельный ассистент; LAN + Internet + Offline; подготовка сейчас, реализация позже. Ядро Rust не использует Windows API; Tauri используется в четырёх файлах [КОД]. Production-каталог модулей пуст. Провайдер, чат, история, память, Policy и Secrets запланированы на Stages 3, 5, 6, 7.
- **Проблема.** Нужна общая форма для независимых экземпляров и клиентов Desktop, которая не ослабляет ADR-011…016 и не вводит распределённой инфраструктуры.
- **Варианты.**
  1. Только удалённый интерфейс без ядра на телефоне.
  2. Общее ядро: экземпляры + клиенты.
  3. Облачный центр.
  4. Микросервисы на Desktop.
- **Предлагаемое решение.**
  - Вариант 2.
  - **Connected Mode — первый MVP.**
  - Standalone ступенями: ST-1 — локальное рабочее пространство, AI только с настроенным провайдером; ST-2 — после проверенного on-device inference.
  - У каждой записи один владелец-экземпляр. Автоматической синхронизации в MVP нет. Офлайн-очередь — только черновики, не команды.
  - Ядро остаётся одним крейтом, пока второму бинарнику не понадобится его часть (OD-9).
  - На телефоне критическая сетевая логика — в Rust и нативном слое, не в WebView (документ 02).
- **Последствия.** Изменений ядра сейчас нет. Мобильная поставка следует за Desktop-этапами. Пользователь видит отдельные истории Desktop и телефона.
- **Зависимости.** OD-2, OD-11, OD-12; этапы 3, 5, 6, 7.
- **Изменяемые решения.** Нет. ADR-011 (каталог при компиляции) действует для каждой платформы.
- **Статус:** PENDING OWNER APPROVAL.

## ADR-018. Remote Access: core-сервис, Remote API, Event Gateway, связь и шаг 0 завершения

- **Контекст.**
  - Tauri-команды — обёртки над функциями с `ModuleManagerHandle` [КОД].
  - `ui_bridge` доставляет события шины в webview.
  - Решение 3 / ADR-014: у модулей нет доступа к менеджеру.
  - ADR-011: core-сервисы не отключаются.
  - Решение 28: порядок выхода.
  - [ВЛАДЕЛЕЦ]: Communication Layer внутри Desktop Core; VPN для Internet в MVP; relay отложен (ТЗ 2026-11-20 §4); направления CF-1…CF-4 (ТЗ REV3 §6).
- **Проблема.** Нужно принимать удалённые запросы. При этом нельзя обходить Module Manager, вводить вторую шину, держать сеть открытой по умолчанию и нарушать порядок выхода.
- **Варианты.**
  - (A) core-сервис, listener выключен по умолчанию;
  - (B) необязательный модуль — конфликт с решением 3;
  - (C) отдельный процесс — исключён указанием владельца.

  Протокол:
  - REST + WebSocket;
  - один WebSocket с JSON-RPC;
  - gRPC.
- **Предлагаемое решение.**
  - **Core-сервис Remote Access.**
    - Создаётся всегда; listener выключен по умолчанию и включается подтверждённой локальной настройкой.
    - *Оговорка к ADR-011 (CF-1):* core-сервис может держать внешний интерфейс закрытым по настройке; Module Manager им не управляет.
  - **Remote API v1.** REST поверх TLS 1.3 + WebSocket. Обработчики вызывают те же прикладные функции, что команды Tauri. Модули изменяются только через `plan`/`apply` с `acknowledged`. Ошибки — по документу 03 §4.1.
  - **Event Gateway.** Подписчик единственной шины с allowlist и фильтром по правам. Ничего не публикует. Входящие сообщения идут в прикладные функции.
    - *Оговорка к ADR-013 (CF-3):* буфер доставки внешнему потребителю — не отдельный канал уведомлений, если он несёт только события шины в порядке `seq` и при переполнении делает resync.
  - **Связь.** LAN — по адресам из QR. Internet — через VPN пользователя. Relay — только отдельным ADR.
  - **Интерфейс.** Только явно выбранный частный адрес; в «Общественной» сети не включается (документ 08 §3).
  - **Допуск.** Не больше одного удалённого вызова в Module Manager одновременно; лимиты и таймауты очереди (документ 08 §6).
  - **Шаг 0 завершения (дополнение решения 28, CF-2).** Перед шагом 1:
    - закрыть listener и соединения;
    - перевести `received`/`awaiting_confirmation` в `not_executed(shutting_down)`;
    - закрыть журнал на запись.

    После начала остановки модулей журнал не пишется. Незавершённые `executing` обрабатывает сверка при старте (ADR-020). Шаги 1–6 не меняются.
- **Последствия.**
  - Новые сетевые зависимости (ревью владельца).
  - Remote Access показывает собственное состояние, а не статус Module Manager.
  - Контракты IPC не меняются.
  - В выходе появляется шаг 0.
- **Зависимости.** OD-3, OD-4, решения по CF-1…CF-4; CSP (#13); Secrets (Stage 7 [+ MI-02a]); ADR-019, ADR-020.
- **Изменяемые решения.** Решение 28 — **дополняется** шагом 0. ADR-011 и ADR-013 получают толкования без изменения текста. ADR-014 не меняется.
- **Статус:** PENDING OWNER APPROVAL.

## ADR-019. Модель безопасности удалённого доступа: RequestContext, идентичность устройств, права

- **Контекст.** ADR-008 (только типизированные команды); ADR-012 (подтверждение проверяет Rust); Policy — Stage 5; Telegram (Stage 7) с allowlist; `csp: null`.
- **Проблема.** Нужны проверяемые атрибуты запроса, идентичность устройств и права, которые нельзя подделать с клиента и которые подходят и Mobile, и Telegram.
- **Варианты.**
  - Сопряжение: QR + одноразовый секрет / цифровой код + PAKE.
  - Аутентификация: mTLS / pinned TLS + challenge ключом устройства на каждом соединении / bearer-токены.
  - Уровни: A / B / C (документ 06 §4.1).
  - Telegram: T1 / T2 / T3 (документ 06 §3).
- **Предлагаемое решение.**
  - `RequestContext {source, principal, device_id, session_id, request_id, grant_version}`; доверенные атрибуты определяет сервер. Доверие к `DesktopUi` требует CSP.
  - Ключи устройства аппаратные, неэкспортируемые (`device_session_key`, `device_confirmation_key`).
  - Сопряжение инициирует Desktop:
    - QR с одноразовым секретом;
    - привязка к TLS exporter;
    - 6-значный код на обоих экранах;
    - подтверждение на Desktop.
  - Аутентификация на каждом TLS-соединении по challenge; bearer-токенов нет.
  - Pin по SPKI; плановая и экстренная ротация.
  - Отзыв немедленный: Connection Manager закрывает соединения.
  - Сопряжение, отзыв, изменение прав, включение доступа, ротация и аудит — только локально.
  - Модель уровней — по OD-5; рекомендация команды — C (Execute отдельно).
  - Telegram — по OD-14; рекомендация команды — T3.
- **Последствия.** Нативный плагин ключей на телефоне. Проектирование Policy Stage 5 получает `RequestContext` на вход.
- **Зависимости.** OD-5, OD-14; Secrets; ADR-018.
- **Изменяемые решения.** Нет.
- **Статус:** PENDING OWNER APPROVAL.

## ADR-020. Жизненный цикл удалённого запроса и Request Journal

- **Контекст.**
  - Менеджер возвращает `Store` и при «ничего не изменилось», и при «итог неизвестен до следующего запуска». Потерянный ответ актора превращается в `ShutDown` [КОД: `manager.rs:417–426`, `1061–1081`].
  - Storage: одно соединение, типизированные операции, мера 4 (ADR-016).
  - Без автоматического восстановления (решение 12).
- **Проблема.** Действие с побочным эффектом нельзя выполнять повторно из-за потери ответа. Подтверждение не должно зависеть от хэша, в который само входит.
- **Варианты.**
  - Журнал на Desktop с дедупликацией и состоянием `outcome_unknown`.
  - Только дедупликация в памяти: теряется при перезапуске.
  - Двухфазный prepare/commit с токеном сервера: сложнее, но не устраняет неопределённость ответа менеджера.
- **Предлагаемое решение.**
  - Состояния: `received` / `awaiting_confirmation` → `executing` → `completed` | `not_executed(reason)` | `outcome_unknown(reason)`. `executing` записывается до вызова.
  - Канонический Intent (RFC 8785) и `intent_hash` без транспортных данных и подтверждений. Подтверждение — отдельная подпись над `intent_hash` и одноразовым challenge Desktop.
  - Повторная проверка прав в транзакции перехода в `executing`.
  - `ShutDown`, `Store`, внутренние ошибки и обрыв → `outcome_unknown`.
  - Сверка при старте до открытия listener.
  - Повторное выполнение никогда не автоматическое; телефон может повторно отправить только тот же `request_id` и ту же подпись.
  - Запросы с побочным эффектом не принимаются, если Storage не `Ready`.
  - После шага 0 журнал не пишется.
- **Последствия.**
  - Новый потребитель Storage (миграция с ревью владельца).
  - Часть реальных исходов видна как `outcome_unknown`, и пользователь проверяет их сам.
- **Зависимости.** CF-5 (после обновления ADR-016 в #21 этап E); ADR-018; ADR-019.
- **Изменяемые решения.** Нет. ADR-016 получает нового потребителя (расширение).
- **Статус:** PENDING OWNER APPROVAL.
