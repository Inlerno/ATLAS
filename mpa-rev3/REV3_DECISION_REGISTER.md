# REV3 — реестр решений владельца (OD-1…OD-15)

**Правило: рекомендация команды (Claude) или ревью — не решение владельца.** Статус **PENDING OWNER APPROVAL** стоит везде, где владелец не подтвердил решение явно. «Подтверждено владельцем» — только при прямом указании в ТЗ, с указанием источника. Заменяет REV2 `OWNER_DECISIONS.md`.

## 2. Подробно

### OD-1 — расположение и язык
- **Варианты.**
  - (а) пакет вне репозитория до решений; принятое → ADR-017+ в `docs/DECISIONS.md`, остальное плоско в `docs/`;
  - (б) новые каталоги `docs/architecture/`, `docs/decisions/`;
  - (в) один `docs/MOBILE.md`.

  Язык: русский / английский / оба.
- **Рекомендация.** (а) + русский.
- **Аргументы.** Единый реестр ADR, плоский `docs/` и язык репозитория сохраняются.
- **Влияние.** Нужна таблица MPA → ADR.
- **Зависимости.** MD-01.
- **Последствия отказа.** При (б) — новая структура без прецедента; при английском — расхождение языка с репозиторием.
- **Примечание.** REV3 опубликован в ветке `docs/mpa-rev3` (каталог `mpa-rev3/`) по ответу владельца от 2026-11-21. Это рабочая публикация для ревью, а не размещение по OD-1.
- **Статус.** PENDING OWNER APPROVAL.

### OD-2 — состав MVP
- **Варианты.**
  - (а) Connected MVP, затем ST-1, затем ST-2;
  - (б) Connected + ST-1 вместе;
  - (в) сначала Standalone.

  Подвопрос: входят ли в MVP чтение истории и памяти Desktop — при сохранении Stage 7 они к тому моменту существуют (документ 11 §3).
- **Рекомендация.** (а). История и память — инкрементом после MVP, ради меньшего объёма.
- **Аргументы.** Переиспользование сервисов Desktop; честное позиционирование; on-device AI не проверен.
- **Влияние.** До G6 и юридической проверки — только внутренние сборки.
- **Зависимости.** MPA-4, ST-1.
- **Последствия отказа.** (б) увеличивает MVP и связывает его со Stage 6 и MS-01/02; (в) требует непроверенного on-device AI.
- **Статус.** PENDING OWNER APPROVAL. Роль «оба режима» подтверждена владельцем (первое ТЗ MPA).

### OD-3 — размещение Remote Access
- **Варианты.**
  - (A) core-сервис, listener выключен по умолчанию;
  - (B) модуль Module Manager — конфликт с решением 3 (CF-4);
  - отдельный процесс исключён владельцем (ТЗ 2026-11-20 §4).
- **Рекомендация.** (A), при условии принятия толкования CF-1.
- **Аргументы.** (B) требует изменения ADR-014.
- **Влияние.** Remote Access имеет собственные состояния (03 §2.1); нужен шаг 0 выхода (CF-2).
- **Зависимости.** ADR-018; согласовать с открытым вопросом ?-2 (сервисы для модулей; Telegram).
- **Последствия отказа.** (B) — изменение ADR-014 и решения 3.
- **Статус.** PENDING OWNER APPROVAL.

### OD-4 — VPN или relay
- **Проверка основания.** Первое ТЗ MPA: «Local network + Internet», рассмотреть VPN и relay, «minimal viable architecture». ТЗ 2026-11-20 §4: «VPN как предпочтительный вариант Internet connectivity для MVP; собственный relay отложен». Противоречий не найдено.
- **Статус.** Подтверждено владельцем (концепция); формальная фиксация — в ADR-018 (PENDING).

### OD-5 — модель прав
- **Варианты.** A (накопительная), B (независимые права), C (гибрид, Execute отдельно) — документ 06 §4.1.
- **Подвопросы.**
  - `module.get_settings` — Admin или Read;
  - `module.replace_config` удалённо с биометрией или только на Desktop;
  - какие классы команд требуют подтверждения на Desktop.
- **Рекомендация.** C; Admin; удалённо с биометрией (консервативная альтернатива — только Desktop); необратимые — на Desktop.
- **Аргументы.** Управление ПК (ADR-008) отделено от администрирования модулей.
- **Влияние.** Ещё одно право в UI и тестах.
- **Зависимости.** MD-05, MI-05.
- **Последствия отказа.** При A Admin автоматически даёт команды ПК.
- **Статус.** PENDING OWNER APPROVAL.

### OD-6 — структура мобильного приложения
- **Варианты.** Отдельное приложение / мобильные цели в текущем проекте.
- **Рекомендация.** Отдельное.
- **Аргументы.** Конфигурация и CI Desktop не трогаются.
- **Зависимости.** MS-03b, MI-10.
- **Последствия отказа.** Мобильные capabilities и CI внутри Desktop-проекта.
- **Статус.** PENDING OWNER APPROVAL (отложено).

### OD-7 — юридическая проверка
- **Варианты.** Начать сейчас / отложить. Путь лицензии:
  - GPL-3.0-or-later + разрешение и/или EULA;
  - отдельная лицензия для мобильных сборок;
  - без App Store;
  - отложить распространение.
- **Рекомендация.** Начать сейчас (общая с Desktop проблема B1). Путь — только по заключению.
- **Влияние.** G6.
- **Зависимости.** MD-07, документ 13.
- **Последствия отказа.** Дата выпуска iOS и Android неизвестна; публичный выпуск Desktop заблокирован тем же B1.
- **Статус.** PENDING OWNER APPROVAL.

### OD-8 — push
- **Варианты.** Нет / content-free push через APNs/FCM / только локальные уведомления.
- **Рекомендация.** Нет в MVP.
- **Последствия отказа.** Зависимость от облачной инфраструктуры Apple/Google.
- **Статус.** PENDING OWNER APPROVAL (отложено).

### OD-9 — разделение на крейты
- **Варианты.** Сейчас / по условию / никогда.
- **Рекомендация.** По условию. Подвопрос: может ли тестовая обвязка MPA-2 подключать весь крейт.
- **Последствия отказа.** Разделение сейчас создаёт затраты во время Desktop-работы.
- **Статус.** PENDING OWNER APPROVAL (отложено).

### OD-10 — Rust↔TS
- **Варианты.** Ручная копия + тест (как сейчас для IPC) / генерация / schema-first.
- **Рекомендация.** Решить в MD-05; для API v1 — схема или генерация.
- **Последствия отказа.** Две ручные копии DTO расходятся.
- **Статус.** PENDING OWNER APPROVAL.

### OD-11 — источник AI в Standalone
- **Варианты.** Нет / OpenAI-совместимый адрес в сети пользователя / on-device после MS-04 / облако по выбору («no mandatory cloud» допускает необязательный вариант — решать владельцу).
- **Рекомендация.** «Нет» + свой адрес в ST-1; on-device — в ST-2.
- **Статус.** PENDING OWNER APPROVAL (отложено).

### OD-12 — перенос данных
- **Проверка основания.** Первое ТЗ MPA запрещает автоматическое слияние без модели владения. ТЗ 2026-11-20 §4: «отсутствие автоматической синхронизации в MVP». Противоречий нет.
- **Статус.** Для MVP подтверждено владельцем; явное копирование и Sync API — PENDING (отложено).

### OD-13 — шифрование на телефоне
- **Варианты.** Только ОС / ОС + аппаратные ключи / шифрование БД (меняет сборку ADR-016).
- **Рекомендация.** Второй вариант для ST-1.
- **Статус.** PENDING OWNER APPROVAL (отложено).

### OD-14 — RequestContext, Policy, Telegram
- **Варианты.** Принять сейчас как вход / решать при Stage 5 / отдельные контексты на канал.

  Telegram:
  - T1 — только владелец;
  - T2 — несколько пользователей сразу;
  - T3 — только владелец, модель расширяема (документ 06 §3).
- **Рекомендация.** Принять сейчас; T3.
- **Аргументы.** Mobile и Telegram должны иметь общую модель источника; доверять клиентскому origin нельзя; owner-only **не** считается окончательным.
- **Влияние.** План Policy Stage 5 включает `source` и `principal`.
- **Зависимости.** MD-02, MI-05, MI-14.
- **Последствия отказа.** Разные модели прав у Telegram и Mobile; дорогая переделка.
- **Статус.** PENDING OWNER APPROVAL.

### OD-15 — гейты и Secrets
- **Срок Secrets.** Stage 7 — **подтверждено владельцем** (ТЗ REV3 §4 F-04: «сохранить Stage 7»; §6 CF-6). Вариант «перенести Secrets раньше» из REV2 снят.
- **Гейты.** G0–G6 по документу 11 §4. Изменения против REV2:
  - CF-1…CF-4 перенесены в G0;
  - спайки — по разрешению, без привязки к G0;
  - MS-03 разделён на a/b;
  - OD-7 убран из G0.
- **Рекомендация.** Принять гейты.
- **Последствия отказа.** Нет критериев перехода между фазами.
- **Статус.** Гейты — PENDING OWNER APPROVAL.
